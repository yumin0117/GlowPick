# 05. 테스트 실행 방법

`run_tests.py`는 `test_cases.csv`의 케이스를 Gemini에 보내고 결과를 자동으로 채점한다.
프롬프트(`01_시스템프롬프트.md`)나 스키마(`02_schema_*.json`)를 고치면 스크립트를 다시 돌리기만 하면 된다.
스크립트가 두 파일을 직접 읽기 때문이다.

## 1. 처음 한 번: 설치

```bash
cd prompt   # GlowPick 저장소 폴더에서
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

다음부터는 터미널을 열 때마다 `source .venv/bin/activate`만 실행하면 된다.

## 2. API 키 설정 (절대 공유·커밋 금지)

[Google AI Studio](https://aistudio.google.com/)에서 **결제 정보를 연결하지 않은 무료 키**를 만든 뒤, 둘 중 하나로 설정한다.

- 터미널에서만 쓰기: `export GEMINI_API_KEY=발급받은키`
- 파일로 저장: 이 폴더에 `.env` 파일을 만들고 `GEMINI_API_KEY=발급받은키` 한 줄을 적는다.
  `.env`는 `.gitignore`에 들어 있어서 GitHub에 올라가지 않는다.

스크립트는 키를 화면이나 결과 파일에 출력하지 않는다.

## 3. 테스트 자료 준비 (데이터 담당과 함께)

| 무엇 | 어디에 | 형식 |
|---|---|---|
| 테스트 사진 | `images/` | `test_cases.csv`의 image 열과 같은 이름 (예: `L01.jpg`). jpg·png·webp 가능 |
| 정답 전성분 | `truth/` | `L01.txt`처럼 한 줄에 성분 하나, 라벨 순서대로 (`truth/_예시.txt` 참고) |
| 표기 통일 규칙 | `truth/aliases.csv` | `변형,표준` (예: `물,정제수`) |
| 빈칸 채우기 | `test_cases.csv` | `TODO:`로 시작하는 칸(모델링팩 제품명, 참고 제품)을 실제 값으로 바꿈 |

- 사진이 없거나 `TODO`가 남은 케이스는 자동으로 **SKIP** 처리된다.
- M02·M03의 제조사 안내는 혼합 규칙을 시험하려고 만든 가상 문구다. 실제 제조사 안내를 구하면 그 문구로 바꾼다.

## 4. 실행

```bash
python3 run_tests.py --dry-run
```
API를 호출하지 않고 사진·정답 파일·TODO 상태만 점검한다. 채워진 요청문까지 보려면 `--show-prompt`를 붙인다.

```bash
python3 run_tests.py --only L01 --repeat 1
```
먼저 1개 케이스만 실제로 돌려서 연결을 확인한다.

```bash
python3 run_tests.py --label v0.1
```
전체 케이스를 3번씩 실행한다. 호출 사이에 7초씩 기다린다.

| 옵션 | 설명 | 기본값 |
|---|---|---|
| `--only L01,M02` | 일부 케이스만 실행 | 전체 |
| `--repeat 3` | 케이스당 반복 횟수 (일관성 확인용) | 3 |
| `--label v0.2` | 결과 폴더 이름표 (프롬프트 버전) | 시각만 |
| `--model 모델명` | Gemini 모델. 환경변수 `GEMINI_MODEL`로도 지정 가능 | `gemini-3.5-flash` |
| `--delay 7` | 호출 사이 대기 시간(초) | 7 |
| `--temperature 0.2` | 서버 설정과 같게 유지 | 0.2 |

> **무료 한도 주의**: 전체 24케이스 × 3회 = 72번 호출이다. 무료 등급은 분당·하루 요청 수 제한이 있으니 AI Studio에서 현재 한도를 먼저 확인한다.
> 처음에는 `--only`와 `--repeat 1`로 나눠서 돌린다. 429 오류가 나면 스크립트가 30초·60초·90초 기다린 뒤 다시 시도한다.
>
> 모델은 서버 담당이 실제로 쓰는 모델과 같은 것으로 맞춘다.

## 5. 결과 보기

`results/날짜_시각_이름표/` 폴더에 결과가 생긴다.

| 파일 | 내용 |
|---|---|
| `report.md` | 요약 지표와 케이스별 판정 (발표 자료에 그대로 활용) |
| `summary.csv` | 회차별 상세 결과 (엑셀로 열기) |
| `raw/L01_r1.json` | Gemini가 실제로 돌려준 원본 응답 |
| `meta.json` | 모델, temperature, 프롬프트 해시 |

### 판정 의미

| 판정 | 의미 | 할 일 |
|---|---|---|
| PASS | 자동 검사 모두 통과 | 그래도 `raw`에서 설명 품질을 눈으로 확인 |
| WARN | 규칙 위반은 아니지만 사람이 봐야 함 (안내 문구 누락, 인식률 90% 미만, 과장 표현 의심 등) | 원본을 보고 문제면 프롬프트 수정 |
| FAIL | 규칙 위반 (status 불일치, 지어낸 성분, 혼합 판단 오류, 형식 오류 등) | 프롬프트 수정 후 재시험 |
| ERROR | API 호출 실패 (한도, 네트워크) | 잠시 후 `--only`로 다시 실행 |
| SKIP | 사진·정답·입력 미준비 | 자료 준비 |

### 자동으로 검사하는 항목

- JSON 형식이 맞는지, 필수 필드가 다 있는지
- 기대한 status와 같은지, 모델링팩의 혼합 판단(`mix_decision`)이 맞는지
- 정답 파일과 비교한 **성분 인식률**과 **기준표에 없는 성분(지어낸 성분)**
- 보완 성분이 라벨에 이미 있는 성분인지
- 도움·주의 성분이 실제로 읽은 성분 안에 있는지
- 참고 제품이 없는데 제품을 추천했는지
- `safety_warning`일 때 추천·혼합 안내를 비웠는지
- 제조사 안내 없이 `allowed`로 판단했는지, 비율을 만들어 냈는지
- 피부 타입이 "모름"일 때 안내 문구가 있는지
- 사용자가 고르지 않은 피부 고민을 근거로 댔는지
- "치료·완치·재생·100%" 같은 표현
- 같은 케이스를 반복했을 때 status와 도움 성분이 얼마나 같은지(일관성)

설명이 쉬운지, 이유가 맞는지는 자동으로 판단할 수 없다. `raw` 파일을 직접 읽고 확인한다.

## 6. 개선 순서

1. `report.md`에서 FAIL·WARN 케이스를 고른다.
2. `raw/` 원본을 보고 원인을 찾는다.
3. `01_시스템프롬프트.md`를 고친다.
4. 같은 케이스만 `--only`로 다시 돌려 확인한다.
5. 전체를 새 `--label`(예: v0.2)로 다시 돌린다.
6. `04_테스트케이스.md`의 D. 수정 기록에 "문제 → 고친 내용 → 재시험 결과"를 적는다.

이 기록은 발표의 "어려움과 해결" 부분에 쓸 수 있다.
