# 프롬프트 설계 근거 (v2)

서버 담당(mj) 구조를 그대로 따른다. 스키마·코드는 바꾸지 않고 `prompts/extract.txt`, `prompts/explain.txt` 두 파일만 교체한다.

```
사진 ──▶ [1단계 판독 extract.txt] ──▶ Extraction(status, ingredients…)
                                         │ status = complete 이고 근거 자료와 겹치는 성분이 있을 때만
                                         ▼
성분 + 피부 정보 + approvedClaims ──▶ [2단계 설명 explain.txt] ──▶ ModelAnalysis(summary, ingredientNotes, warnings)
                                         │
                                         ▼  서버가 근거ID·성분 일치를 다시 검사 (어긋나면 오류 처리)
```

## 역할분담 PDF 요구사항 → 반영 위치

| 요구사항 (역할 03) | 반영 |
|---|---|
| 성분 전문가 역할, 한국어 설명 수준, 답변 범위 | explain 첫 단락(역할·한계), 해요체 1~2문장, 쓰지 않는 표현 목록 |
| 라벨에서 읽은 전성분과 판단 근거 구분 | 1단계는 "읽기만", 2단계는 `approvedClaims` 문장만 근거로 설명. 단계를 나눠 섞이지 않게 함 |
| 도움·주의·보완 성분 분류 규칙 | 현재 서버 스키마에 해당 필드가 없음. 근거 자료(`approvedClaims`)가 늘면 스키마와 함께 추가 제안 |
| 피부 타입 모름 예외 | explain 3번: 피부 타입 추측·타입 이름 언급 금지, 고민 기준으로만 |
| 전성분·출처 미확인 시 추천 단정 금지 | explain: 근거 없는 성분은 설명하지 않음, 제품 추천 요청에는 고정 문구로 거절 |
| 모델링팩 혼합은 제조사 근거가 있을 때만 | 서버 코드가 혼합을 항상 `unknown`으로 고정. 프롬프트도 혼합 허용·비율 생성 금지 |
| 흐린 라벨·누락 성분·잘못된 사진·심한 열감 테스트 | `eval_cases.json` 판독 15개 + 설명 8개 |

## 의도적으로 하지 않은 것

- 사진에서 성분을 읽을 때 피부 정보·정답표를 주지 않는다. 서버 설계를 따르며, 정답을 알려 주면 판독 정확도를 측정할 수 없기 때문이다.
- 성분 기능을 모델 지식으로 보충하지 않는다. 서버가 근거ID를 검사하므로 근거 밖 설명은 결과의 신뢰도를 떨어뜨린다.
- 띄어쓰기 표기 차이(예: `밤부사 불가리스수` / `밤부사불가리스수`)는 프롬프트로 강제하지 않았다. 라벨에서 줄이 바뀌는 자리라 사람이 봐도 띄어쓰기를 확정할 수 없기 때문이다. 대신 성분명 정규화로 처리하도록 서버·데이터 담당에게 제안한다.
